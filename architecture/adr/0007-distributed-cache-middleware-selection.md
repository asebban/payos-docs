# ADR-0007 — Distributed cache middleware selection: which product backs `ICacheStore`/`ISessionStore`/`IIdempotencyStore`/`ISlidingWindowCounter`

**Status:** Proposed

## Context

[ADR-0006](0006-distributed-cache-over-sticky-sessions.md) decided *that* PayOS needs a distributed shared cache behind a pluggable-store SPI for cross-instance state (sessions, HTTP/connector idempotency, tenant quotas, connector execution/routing state), and it names Redis because Redis is the backend that was shipped so far (`cache-service-redis`, `session-service-redis`, `idempotency-service-redis`, `sliding-window-counter-redis`). It does not evaluate *which* middleware product should sit behind that SPI (it inherited Redis as a given). This ADR closes that gap: it defines the actual functional requirements the SPI implementations impose, evaluates the realistic middleware candidates against them, and picks a concrete product, without treating "already Redis" as a point in Redis's favor.

The requirement is not a generic "distributed cache" — we need three distinct atomicity shapes that any candidate distributed cache must support natively:

- **Plain KV with TTL** (`ICacheStore.put`/`get`/`remove`/`exists`) — the easy case, every candidate below supports it.
- **Atomic "increment, and set TTL"** (`ICacheStore.increment`) — `RedisCacheStore` implements this as a single Lua script (`RedisCacheStore.java:24-30`) specifically to avoid a race window where a crash between `INCRBY` and `EXPIRE` leaves a counter that never expires.
- **Atomic "claim if and only if absent, with TTL"** (`IConnectorIdempotencyStore.tryClaim`, used by HTTP/connector idempotency) — `RedisConnectorIdempotencyStore` implements this as a single `SET key val NX EX ttl` command (`RedisConnectorIdempotencyStore.java:23-24`).
- **Atomic "prune expired entries, add one, count" over a per-key ordered set** (`ISlidingWindowCounter.recordAndCount`/`count`, used by rate limiting) — `RedisSlidingWindowCounter` implements this as a single Lua script over a sorted set (`RedisSlidingWindowCounter.java:16-22`), because pruning and counting as two round trips would double-count or under-count under concurrent access from other instances.


## Options considered

### Option A — Redis (OSS, pre-license-change versions / Redis 7.2 line)

- **Pros:** exactly matches every atomicity requirement above (Lua scripting, `SET NX EX`, sorted sets) — this is what the four existing SPI implementations already use, so choosing it costs zero rewrite; single-threaded execution model makes "atomic across the cluster" trivially true for any command or script.
- **Cons:** as of Redis 7.4/8, Redis Ltd. re-licensed the server under a dual RSALv2/SSPLv1 scheme instead of the historic BSD license — self-hosting for internal use is unaffected, but it signals a governance direction (vendor-controlled, not community-governed) that has already caused most of the original Redis core maintainers and major cloud vendors to fork away from it; adopting Redis today means either pinning to the last BSD-licensed 7.2.x line indefinitely (accumulating unpatched CVEs over time) or accepting the new license terms going forward, which is precisely why this decision needs to be made explicitly rather than inherited from ADR-0006.

### Option B — Valkey (Linux Foundation fork of Redis 7.2, BSD-3-clause)

- **Pros:** byte-for-byte protocol-compatible with Redis (RESP2/RESP3) and command-compatible including `EVAL`/Lua scripting, `SET ... NX EX`, and sorted-set commands — the existing `cache-service-redis`/`session-service-redis`/`idempotency-service-redis`/`sliding-window-counter-redis` modules talk to the server exclusively through Lettuce's `RedisCommands` interface over this protocol, so **none of that code changes**; only the deployed server binary and connection string change; governed by the Linux Foundation with AWS, Google Cloud, Oracle, and Ericsson as maintaining sponsors, staying permissively licensed (BSD-3-clause) with no re-licensing risk; actively receives the security and performance work formerly done by Redis's own core team, since most of them moved to this fork; genuinely a strict improvement over Option A for PayOS's specific situation — same atomicity guarantees, same wire protocol, zero code cost, no licensing overhang.
- **Cons:** younger project name (forked March 2024) — less brand recognition than "Redis" in hiring/onboarding and in some managed-hosting catalogs, though every major cloud provider now offers a managed Valkey tier; Valkey may be behind Redis on features introduced after the fork, though none of the commands this SPI relies on fall into that category.

### Option C — Dragonfly (multi-threaded, Redis-protocol-compatible, BUSL-licensed)

- **Pros:** also RESP-protocol-compatible, so equally zero-code-change against the existing Lettuce-based implementations; multi-threaded architecture claims substantially higher throughput and better memory efficiency per node than single-threaded Redis/Valkey under high concurrency, which is relevant if tenant-quota and idempotency traffic ever becomes the bottleneck.
- **Cons:** licensed under the Business Source License (BUSL) with a vendor-controlled conversion-to-open-source date, i.e. it carries the same licensing risk this ADR is trying to move PayOS away from by rejecting Option A, just from a different vendor; smaller production references than Redis/Valkey; the throughput advantage is unproven for PayOS's actual access pattern (small keys, short TTLs, moderate QPS) versus a genuine bottleneck.

### Option D — Embedded JVM-native distributed cache (Hazelcast / Apache Ignite)

- **Pros:** no separate server process to provision, patch, or monitor — the library is embedded in each PayOS instance and instances discover each other to form the cache cluster themselves, which removes "a whole new infrastructure component" from the ops burden entirely; native Java APIs (`IMap`, `IAtomicLong`) integrate directly with no serialization-protocol translation layer (serialization is done internally).
- **Cons:** none of the three atomic requirements map cleanly onto the primitives these libraries expose — `IAtomicLong` gives atomic increment but not "increment plus conditional first-write TTL" in one call, and there is no *sorted-set* analog with server-side atomic prune+add+count, so the sliding-window and quota logic would need to be reimplemented as CP-Subsystem-backed compare-and-swap loops, which is materially more code and a substancially different (and less battle-tested, for this specific use) correctness argument than "Redis never interleaves another command inside a script"; cluster membership (discovery, split-brain handling, quorum) becomes PayOS's own operational problem instead of being delegated to a well-understood external service; The concern is: nobody has tested whether those libraries work correctly when embedded inside a GraalVM Truffle sandbox. They might fail silently, throw unexpected errors, or behave incorrectly when the sandbox blocks their reflection calls. This is "unverified integration risk"; trades "one shared external dependency" for "clustering logic embedded in every instance," which is a different risk category.

### Option E — NATS JetStream KV (reuse of the existing NATS dependency)

- **Pros:** zero new infrastructure — NATS JetStream is already deployed and operated for `queue-service-nats`; per-key TTL and a watch/subscribe API are both natively supported, which is a genuine capability Redis lacks (native cross-instance change notification without a separate pub/sub channel).
- **Cons:** JetStream KV's only atomicity primitive is revision-based optimistic concurrency (compare-and-swap on an expected revision number) — there is no server-side atomic increment and no sorted-set structure, so both the tenant-quota increment and the sliding-window prune+add+count would need to be built as client-side retry loops, which under real contention (many instances hitting the same tenant's quota key) degrades to repeated retries rather than Redis/Valkey's guaranteed single round trip; this is a strictly weaker atomicity capacity for exactly the two mechanisms ADR-0006 flagged as needing cross-instance correctness, not just the easy KV case.

### Option F — Memcached

Memcached distributes data by **sharding**: the client hashes each key to determine which node owns it and routes requests there transparently, so all keys are reachable from any application instance while all nodes are alive. However, there is **no replication** — each key exists on exactly one node with no copy elsewhere. If that node crashes, every key it held is permanently lost until clients re-write it.

- **Pros:** simplest possible operational model, extremely mature, very low per-node memory overhead.
- **Cons:** no persistence and no replication (a node restart silently drops everything, which is acceptable for a pure cache but not for idempotency claims or terminal-routing evidence that must survive a node failure); no atomic "increment with conditional TTL" and no sorted-set equivalent, so it fails the same two mechanisms as Option E, with no compensating capability to replace it. Ruled out without further comparison — it is strictly dominated by every other option on the requirements that matter here.

## Decision

Adopt **Option B — Valkey** as the concrete middleware product behind the existing `ICacheStore`/`ISessionStore`/`IIdempotencyStore`/`ISlidingWindowCounter` SPI, replacing "Redis" as the reference implementation target going forward.

This is a real "better than Redis" answer, not a rename: Valkey satisfies every atomicity requirement from the Context section exactly as Redis does — because it *is* the same command surface and protocol — while removing the licensing-governance risk that Option A now carries, at zero code cost, since `cache-service-redis`/`session-service-redis`/`idempotency-service-redis`/`sliding-window-counter-redis` talk to the server only through Lettuce's RESP-level `RedisCommands` interface, which does not care which RESP-speaking server is on the other end. Concretely: point the existing Lettuce connection string at a Valkey server/cluster instead of a Redis server/cluster; no changes to `RedisCacheStore`, `RedisConnectorIdempotencyStore`, `RedisSlidingWindowCounter`, or their session-store counterpart are required. The module and class names (`cache-service-redis`, `RedisCacheStore`, `security.sessionStoreType: redis`, etc.) are left as-is in this ADR — renaming them is a separate, purely cosmetic decision this ADR does not take a position on.

Option C (Dragonfly) is rejected for now on licensing grounds identical in kind to the reason Option A is rejected as the forward-looking default, not on technical grounds — *it remains worth revisiting as an alternative (same protocol compatibility argument as Valkey) if a future load-testing exercise shows single-threaded RESP throughput is a real bottleneck, since switching to it would carry the same zero-code-change property*.

Options D (embedded Hazelcast/Ignite) and E (NATS JetStream KV) are rejected because neither provides the two contended atomic operations (conditional-TTL increment, atomic sliding-window prune+add+count) as a native single round trip — both would require reimplementing those two mechanisms as client-side retry loops, which is a strictly weaker alternative than what Option B provides for free, for the specific mechanisms ADR-0006 identified as needing real cross-instance correctness (tenant quotas, connector idempotency). Option E remains worth reconsidering specifically for connector execution/terminal-routing *event notification* in the future, where its native watch/subscribe capability could remove a polling loop — but that is a narrower, additive use case, not a reason to replace Option B as the general-purpose store.

Option F (Memcached) is rejected outright: no persistence/replication and no atomic increment-with-TTL or sorted-set primitive, with no compensating advantage over Options B/C for PayOS's requirements.

## Consequences

- **Positive:** removes the licensing-governance risk of depending on Redis Ltd, at zero code cost, since the swap is entirely at the deployment/ops layer (server binary + connection string); every atomicity guarantee the four existing SPI implementations rely on (Lua-script atomicity, `SET NX EX`, atomic sorted-set operations) continues to hold exactly as before, because Valkey implements the same commands; the pluggable-store SPI shape from ADR-0006 is validated by this decision — a store-level swap needed zero kernel or interface changes, exactly as that pattern promises.
- **Negative:** operational runbooks, deployment manifests, and any documentation that says "Redis" as the deployment target need updating to say "Valkey" (or "a Redis-protocol-compatible server") to avoid confusion about what is actually being run in production; existing config keys and class names still say `redis` (`security.sessionStoreType: redis`, `RedisCacheStore`, etc.) and now denote "the Redis-protocol family," not literally Redis Ltd.'s product — this ADR does not rename them, so that naming mismatch is a known, accepted trade-off until/unless a future ADR chooses to rename the modules.
- **Neutral / open follow-up:** Dragonfly stays a live option to revisit under real load-test evidence; NATS JetStream KV stays a live option specifically for future watch/subscribe-oriented needs (e.g. connector routing-state change notification) rather than as a replacement for the general-purpose store; Hazelcast/Ignite are not being pursued further given the atomicity gap identified above, and no work was undertaken to verify their behavior under the GraalVM Truffle sandbox, since the atomicity gap alone was already disqualifying.
- See [ADR-0006](0006-distributed-cache-over-sticky-sessions.md) for the decision that a distributed shared cache is needed at all, and [`session-store-redis-design.md`](../../../payos/docs/architects/session-store-redis-design.md) for the SPI shape this middleware plugs into.

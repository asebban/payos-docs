# PayOS OpenAPI Documentation Guide

This guide covers authoring annotations, `pdoc` ownership, static safety rules, package-manager integration, regulated delivery, diagnostics, and the current generation pipeline.

## 1. Purpose And Scope

PayOS OpenAPI documentation is generated by `pdoc`, a dedicated static documentation tool. `pdoc` reads bundle metadata and JavaScript source text, extracts explicitly delimited OpenAPI annotation blocks, validates them, enriches the resulting OpenAPI document with PayOS conventions, and writes deterministic YAML or JSON artifacts.

The generator is designed for regulated PayOS delivery workflows:

- it does not start PayOS Runtime;
- it does not execute JavaScript handlers;
- it does not access databases, queues, webhooks, secrets, or runtime services;
- it preserves previous valid output when validation fails;
- it emits stable diagnostics and exit codes for CI and package-manager workflows.

## 2. Generation Ownership

`pdoc` owns OpenAPI generation. Other tools may invoke `pdoc` or consume generated artifacts, but they should not reimplement parsing, validation, enrichment, or output writing.

The generation flow is:

1. parse command options;
2. resolve the selected application, capability, or product target;
3. discover static API JavaScript resources;
4. extract `@payos.openapi` annotation blocks;
5. parse and validate annotation fragments;
6. assemble the OpenAPI document;
7. enrich it with PayOS conventions;
8. validate generated OpenAPI compatibility;
9. write deterministic output through the safety gate.

Responsibilities that must remain in `pdoc`:

- target resolution;
- static API resource discovery and static boundary checks;
- annotation extraction and parsing;
- annotation validation and diagnostic code ownership;
- OpenAPI document assembly and enrichment;
- compatibility validation;
- deterministic YAML/JSON writing;
- validation failure safety and output preservation.

Package managers, build scripts, CI jobs, runtime docs serving, and IDE assistance should call or consume `pdoc`; they should not duplicate its generation logic.

## 3. Static Runtime Safety Boundary

`pdoc` is a static generator. It reads files and metadata only. For how to install `pdoc` command, look at [Install guide of pdoc](./install-pdoc-command.md).

### What `pdoc` does

- Parses CLI options and resolves app, capability, or product targets from bundle metadata.
- Discovers JavaScript API resources under each resolved target's `api/` directory.
- Reads JavaScript files as UTF-8 text.
- Extracts delimited `@payos.openapi` blocks from comments.
- Parses YAML-like OpenAPI fragments.
- Validates annotations and generated OpenAPI structure.
- Writes deterministic YAML or JSON only after validation permits generation.

### What `pdoc` never invokes

- `ma.s2m.payos.BootServer` or PayOS Runtime startup.
- JavaScript evaluation.
- API handler functions.
- Database connections or reads/writes.
- Queue publish/subscribe operations.
- Webhook dispatch.
- Capability lifecycle hooks such as `hooks/lifecycle.js`.
- Runtime configuration or application state mutation.

`ApplicationApiResourceScanner` discovers only files under `api/**/*.js`. `StaticGenerationGuard` rejects resources that are outside the selected target's `api/` directory, are not `.js` files, or use absolute/escaping paths that cross the static API boundary.

## 4. Annotation Authoring Format

OpenAPI operation fragments live inside explicitly delimited JavaScript comments. `pdoc` ignores JavaScript code and reads only the text inside `@payos.openapi` blocks.

### Delimiters

```javascript
/**
 * @payos.openapi
 * method: POST
 * path: /transfers
 * summary: Create transfer
 * responses:
 *   "201":
 *     description: Transfer created
 * /@payos.openapi
 */
```

Only content between `@payos.openapi` and `/@payos.openapi` belongs to the OpenAPI fragment. Other annotation blocks can coexist in the same comment.

```javascript
/**
 * @payos.audit
 * event: transfer.created
 * /@payos.audit
 * @payos.openapi
 * method: GET
 * path: /transfers/{id}
 * responses:
 *   "200":
 *     description: Transfer found
 * /@payos.openapi
 */
```

### Supported MVP fields

| Field | Required | Description |
|---|---:|---|
| `method` | Yes | HTTP method. Duplicate detection compares methods case-insensitively. |
| `path` | Yes | OpenAPI path template, for example `/accounts/{id}`. |
| `summary` | No | Short operation summary. |
| `tags` | No | Operation tags. A scalar value is accepted as one tag. |
| `parameters` | No | OpenAPI parameter objects. |
| `requestBody` | No | OpenAPI request body object. |
| `responses` | No | OpenAPI responses object. |
| `x-*` | No | OpenAPI extension fields. PayOS-specific metadata belongs under `x-payos`. |

PayOS-specific metadata must stay under `x-payos` as an object so generated output remains OpenAPI-compatible.

```javascript
/**
 * @payos.openapi
 * method: POST
 * path: /transfers
 * summary: Create transfer
 * tags:
 *   - Transfers
 * parameters:
 *   - name: X-Tenant-Id
 *     in: header
 *     required: true
 * requestBody:
 *   required: true
 *   content:
 *     application/json:
 *       schema:
 *         type: object
 * responses:
 *   "201":
 *     description: Transfer created
 * x-payos:
 *   idempotency: true
 * /@payos.openapi
 */
```

### Authoring rules

- Keep one operation contract per `@payos.openapi` block.
- Always close the block with `/@payos.openapi`.
- Keep required `method` and `path` values present and non-blank.
- Avoid duplicate `method` plus `path` combinations across scanned files.
- Put PayOS metadata under `x-payos` as an object.
- Do not rely on JavaScript execution for documentation metadata.

## 5. CLI And Package Manager Integration

The stable automation contract is the `pdoc` CLI:

```bash
pdoc --app <appId> --bundle-path <bundleDir> --output <outputFileOrDirectory>
pdoc --capability <capabilityId> --bundle-path <bundleDir> --output <outputFileOrDirectory>
pdoc --product <productId> --bundle-path <bundleDir> --output <outputFileOrDirectory>
```

Exactly one target selector must be provided: `--app`, `--capability`, or `--product`.

| Input | Required | Notes |
|---|---:|---|
| Target selector | Yes | Exactly one of `--app`, `--capability`, or `--product`. |
| `--bundle-path <bundleDir>` | No | Defaults to `.`. Automation should pass it explicitly. |
| `--output <fileOrDirectory>` | No | Defaults to `target/openapi/<target-kind>/<target-id>/openapi.yaml`. |

Expected package-manager behavior:

- invoke `pdoc` as a separate tooling step;
- pass explicit target and bundle path values;
- collect the output artifact only when `pdoc` exits with `0`;
- surface `pdoc` diagnostics unchanged;
- fail the workflow when `pdoc` returns a non-zero exit code;
- avoid reading annotations or generating OpenAPI directly.

Package managers should not call PayOS Runtime to generate documentation, execute JavaScript, duplicate validation rules, or rewrite generated content except for packaging or artifact publication.

## 6. Outputs, Exit Codes, And Regulated Delivery

For auditable CI and release runs, record:

- selected target type and id;
- `--bundle-path`;
- `--output` or the deterministic default path;
- `pdoc --version`;
- source revision or package version that produced the bundle.

Exit codes are stable:

| Exit Code | Meaning |
|---:|---|
| `0` | Generation or validation completed successfully. |
| `1` | Validation or generation failed. Diagnostics explain the failure. |
| `2` | CLI usage is invalid, such as ambiguous target selectors. |

Generated artifacts are deterministic YAML or JSON. The writer uses UTF-8 and LF-normalized output so source-control diffs remain stable across platforms.

Artifacts are suitable for:

- source-control review as generated contract changes;
- CI artifact publication;
- release evidence attached to a package or deployment candidate;
- Swagger UI or downstream OpenAPI validation after successful generation.

Reviewers should inspect changes to paths, operation methods, request/response schemas, security requirements, public/anonymous overrides, standard PayOS error responses, `x-payos.target`, tenant/correlation headers, and idempotency headers.

## 7. Generated PayOS Conventions

Generated contracts keep PayOS runtime conventions visible:

- `X-Correlation-Id` is added so traceability is visible across requests, logs, events, and downstream calls.
- `X-Tenant-Id` is added when tenant policy applies.
- `X-Idempotency-Key` is added only when an operation declares `x-payos.idempotency`.
- PayOS bearer/OIDC security metadata is generated by default.
- Public or anonymous operations can be represented with operation-level `security: []`.
- Standard PayOS error response metadata includes correlation and tenant fields when applicable.
- `x-payos.target` records whether the artifact represents an application, capability, or product target.

## 8. Validation Diagnostics And Troubleshooting

Diagnostics are source-aware when source context is available. A diagnostic can include severity, code, message, source file, line, column, annotation block id, target type, target id, and structured details.

| Diagnostic Code | Meaning | Fix |
|---|---|---|
| `UNCLOSED_OPENAPI_BLOCK` | `@payos.openapi` was opened but not closed. | Add `/@payos.openapi` before the end of the comment/file. |
| `MALFORMED_OPENAPI_FRAGMENT` | The block content cannot be parsed as YAML-like data. | Fix indentation, brackets, quotes, or object/list shapes. |
| `MISSING_REQUIRED_FIELD` | `method` or `path` is absent or blank. | Add non-blank `method` and `path`. |
| `DUPLICATE_OPERATION` | More than one block declares the same method/path. | Keep one owner or change one operation identity. |
| `DUPLICATE_ANNOTATION_DECLARATION` | The same source block was supplied more than once. | Remove the duplicate declaration or fix duplicate scanning input. |
| `INVALID_X_PAYOS_USAGE` | `x-payos` exists but is not an object. | Declare `x-payos:` as an object. |
| `OUTPUT_NOT_UPDATED` | Validation failed while an output file already existed. | Fix earlier diagnostics, then rerun generation. |

### Common examples

Missing `method`:

```javascript
/**
 * @payos.openapi
 * path: /accounts
 * responses:
 *   "200":
 *     description: Accounts listed
 * /@payos.openapi
 */
```

Expected diagnostic:

```text
MISSING_REQUIRED_FIELD: OpenAPI annotation is missing required field 'method'.
```

Malformed YAML-like fragment:

```javascript
/**
 * @payos.openapi
 * method: GET
 * path: /accounts
 * responses:
 *   "200": [broken
 * /@payos.openapi
 */
```

Expected diagnostic:

```text
MALFORMED_OPENAPI_FRAGMENT: OpenAPI annotation block contains a malformed YAML-like fragment.
```

Invalid `x-payos`:

```yaml
x-payos: idempotency
```

Fix:

```yaml
x-payos:
  idempotency: true
```

If validation fails and an output file already exists, `pdoc` preserves it and reports `OUTPUT_NOT_UPDATED`. Delivery pipelines must treat the non-zero exit code as failed and must not publish the preserved file as a new artifact for that run.

## 9. Target Resolution And Generation Pipeline

`PdocApplication` parses the CLI and delegates generation to `PdocGenerationPipeline`. The pipeline resolves targets, extracts annotations, validates fragments, assembles the OpenAPI document, enriches it, validates compatibility, and writes only through the safety gate.

### Target resolution rules

- `--app` resolves one application target.
- `--capability` resolves one capability target.
- `--product` resolves ordered application and capability surfaces belonging to the product.
- Product manifests are not required in the installed bundle.
- Product membership is inferred from `_contributors` on installed `applications[]` entries.
- Entries with `category: "capability"` become product capability surfaces.
- Non-capability entries become product application surfaces.
- `extends` is runtime composition metadata and is not traversed for product documentation membership.

### Data flow

1. `PdocApplication` parses CLI arguments into `CommandOptions`.
2. `PdocGenerationPipeline.generate(...)` resolves the effective output path and format.
3. `TargetResolutionService.resolve(...)` dispatches by target type.
4. Resolvers produce application/capability/product target descriptors.
5. `ApplicationApiResourceScanner` discovers ordered `api/**/*.js` resources.
6. `StaticGenerationGuard` verifies every resource stays inside the static API boundary.
7. `AnnotationBlockExtractor` extracts annotation blocks from each resource.
8. `OpenApiFragmentParser` parses extracted blocks into `OpenApiFragment` models.
9. Extraction or parsing diagnostics stop generation through `GenerationSafetyGate`.
10. `ValidationEngine` validates required fields, duplicates, and `x-payos` usage.
11. `OpenApiDocumentAssembler` and `MapOpenApiLibraryAdapter` create an OpenAPI `3.1.0` document.
12. `OpenApiBaseDocumentMerger` provides a future base-document merge point.
13. Enrichers apply PayOS metadata, security, idempotency, errors, and target identity.
14. `OpenApiCompatibilityValidator` validates document shape and local refs.
15. `GenerationSafetyGate` writes only valid output or preserves existing output on failure.
16. `GenerationDecisionReporter` emits deterministic diagnostics and returns the final exit code.

## 10. Future Runtime And IDE Assistance

Future PayOS Runtime may expose generated OpenAPI artifacts through `/docs` or a documentation UI. That feature should serve generated files; it must not parse annotations, evaluate JavaScript, run generation, or mutate OpenAPI content based on live runtime state.

Runtime docs serving may:

- locate a generated artifact packaged with an app, capability, or product;
- serve it over HTTP;
- add Swagger UI, caching, or access-control concerns;
- report a missing artifact and instruct operators to run `pdoc` during build or packaging.

IDE tooling can rely on the same stable authoring contract:

- delimiter completion for `@payos.openapi` and `/@payos.openapi`;
- YAML-like syntax highlighting inside annotation blocks;
- snippets for common operation shapes;
- local validation mirroring `pdoc` diagnostic codes;
- quick fixes for missing `method`, missing `path`, malformed `x-payos`, and duplicate operation identities.

Future IDE or language-server behavior should reuse `pdoc` rules and diagnostic codes rather than creating a separate interpretation of annotation semantics.

## 11. Review Checklist

Before adding new `pdoc` features, verify that:

- the feature operates on files, metadata, parsed annotations, or generated document models;
- it does not add a dependency on PayOS Runtime startup;
- it does not execute JavaScript;
- it does not require credentials, database access, queue access, webhook delivery, or network calls to inspect runtime behavior;
- any new scanner output is validated by `StaticGenerationGuard` before generation continues;
- diagnostics remain stable and CI-friendly;
- existing output remains protected when generation fails.

When reviewing generated contracts, inspect:

- path and method changes;
- request and response schema changes;
- security requirements and public/anonymous overrides;
- tenant, correlation, and idempotency headers;
- standard PayOS error responses;
- `x-payos.target` metadata;
- deterministic output path and artifact diff.
